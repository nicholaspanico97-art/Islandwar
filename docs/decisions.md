# Decisions

One line per decision: date, decision, reason. Newest at the bottom. "PENDING" marks a decision
that's waiting on a test.

## From the revised game plan (docs/game-plan.md)

- 2026-10-23: Pillar 8, the game must be fun at 4v4 in about 45 minutes. Reason: finding 24 players for a 3-hour match is the project's biggest risk.
- 2026-10-23: Two match presets, Full (12v12, 2–4 h) and Compressed (4v4, about 45 min), both defined in `data/`. Reason: a small match is a real mode, not a test setup.
- 2026-10-23: Drop-in/drop-out, so late joiners get the full world state, team and phase. Reason: player count. It shapes the netcode, so design for it from M1.
- 2026-10-23: Guaranteed match end: a nuke win, otherwise a score at a hard time limit, plus a concede vote. Reason: a nuke-only win with a late defence edge can stalemate.
- 2026-10-23: Team build protection before M3. Reason: one griefer must not ruin a long match for eleven people.
- 2026-10-23: The late-game defence edge stays, but attackers get counters (kill radar, overwhelm AA, escorts, decoys). Reason: avoid a permanent stalemate.
- 2026-10-23: Losing a fuel depot must hurt for real. Reason: three pillars push against snowballing, so raids risk feeling pointless.
- 2026-10-23: Start Phase 1 playtests at about 20 minutes and lengthen it only if players are still busy building. Reason: 45 minutes of scouts only may be too quiet.
- 2026-10-23: godot_voxel is provisional until the M0 test. The fallback is a custom C# chunk mesher. Reason: godot_voxel + C# integration is an unknown, and the bounded map makes the fallback cheap.
- 2026-10-23: Client-side prediction for the local character and vehicle; everything else interpolates between snapshots. Reason: server-authoritative flight feels laggy without it.
- 2026-10-23: MultiplayerSynchronizer/Spawner for M1; expect custom snapshot/delta replication by M3. Reason: 24 players, projectiles and voxel deltas will outgrow them.
- 2026-10-23: Late-join world sync is the terrain seed plus voxel edit deltas per chunk. Reason: lets a joining client rebuild the current world.
- 2026-10-23: An automated bot sync test (headless server plus scripted clients, asserting identical voxel state). Reason: Claude Code can't play the game but can run this.
- 2026-10-23: "Testable" means plain C# and unit tests, not lockstep determinism. Reason: floating-point results aren't bit-identical across machines.

## M0

- 2026-10-23: Target Godot 4.7.2-stable, .NET build. Reason: latest stable tag of godotengine/godot at setup time. **Verified 2026-10-25** on Windows 11 with .NET SDK 8.0.427: tests, build, headless server and two clients connecting all work; 4.7.2 is still the latest stable.
- 2026-10-23: .NET 8 SDK, `net8.0`. Reason: `Godot.NET.Sdk/4.7.2` builds with it; it's the LTS release Godot 4.x supports.
- 2026-10-25: godot_voxel v1.7x, GDExtension edition, renders the terrain (M0 test passed in well under a day). Our `VoxelWorld` stays authoritative: a `VoxelTerrain` with automatic loading off receives each chunk through `try_set_block_data` and each edit through `VoxelTool.set_voxel`, and builds the collision shapes. Reason: it rendered and edited from C# on the first run with no engine build. The string-name API (`ClassDB.Instantiate`/`Set`/`Call`) was tolerable: about 15 calls, all in `Client/Voxels/GodotVoxelView.cs`, and typos fail loudly at runtime. godot_voxel did not need to own the data. Fallback stays the custom C# mesher if the GDExtension (its author warns it has had little testing) causes trouble.
- 2026-10-23: The Sim voxel world (`Sim/Voxels/VoxelWorld`) is the authoritative block data; whatever renders it is a view. Reason: the server stays headless and unit-testable, voxel networking is our own code anyway, and the godot_voxel decision becomes a rendering choice only. Revisit if the M0 test shows godot_voxel needs to own the data.
- 2026-10-23: Terrain generation uses integer (fixed-point) math only. Reason: every client regenerates terrain from the seed, which must give identical blocks on every machine; floats aren't guaranteed to (see the "testable" decision above).
- 2026-10-23: Water is a flat plane at sea level, not blocks, for M1. Reason: simplest option; no fluid simulation needed for the vertical slice.
- 2026-10-23: Block ids are a `ushort` enum; new types are only ever appended. Reason: ids go over the network and into stored deltas.
- 2026-10-23: Layout: `IslandWar.csproj` (Godot assembly: Client/, Server/, Net/), `Sim/IslandWar.Sim.csproj` (plain class library), `tests/IslandWar.Sim.Tests` (xUnit). Reason: the plan's Sim/Net/Client/Server split, with the compiler enforcing that Sim has no Godot dependency.
- 2026-10-23: Game arguments come after a bare `--`: `--server`, `--port=N`, `--seed=N`, `--connect=HOST[:PORT]`. Reason: Godot hands those to the game via `OS.GetCmdlineUserArgs()` and keeps its own flags (`--headless`, `--path`) separate.
- 2026-10-23: Default port 7777. Reason: arbitrary, unprivileged, commonly free.
- 2026-10-25: The godot_voxel binaries (134 MB) are not committed. `./build.sh deps` / `.\build.ps1 deps` downloads the pinned release and checks its SHA-256. Reason: keeps the repository small while everyone runs the same build.
- 2026-10-25: Block picking uses our own grid raycast in Sim (`VoxelRaycast`), not godot_voxel's. Reason: the server must check edits without a renderer, and client and server should agree on what was aimed at.
- 2026-10-25: A client started without `--connect` runs the single-player sandbox (M1a). Reason: simplest way to play locally; `--connect` keeps the networked path.
- 2026-10-25: Player tunables (reach, speeds, gravity, look sensitivity) live in `data/player.json`. Reason: the data-file convention; reach is a rule the server will enforce.

## M1

- 2026-10-25: Build rules live in `Sim/Players/BuildRules` (can break, can place, in reach). Reason: the client checks them before an edit and the M1b server must re-check the same rules.
- 2026-10-25: The bottom block layer (y = 0) is unbreakable. Reason: simplest way to stop players digging out of the world.
- 2026-10-25: The player is a box collider (`width` x `height` x `width` from `data/player.json`) on a `CharacterBody3D`, walking on godot_voxel's collision mesh. No auto-step: jumping clears one block. Reason: a box matches the block grid and the placement rule; auto-step can come later if climbing feels fiddly.
- 2026-10-25: Physics interpolation is on, and the camera is top-level, following the interpolated body each frame. Reason: smooth view on high-refresh monitors with 60 Hz physics, without lagging mouse look.
- 2026-10-25: F toggles flying with collisions off (noclip). Reason: a debug and building aid during M1; revisit before matches have rules.
- 2026-10-25: Input actions are registered from code (`Client/InputActions.cs`) rather than in `project.godot`. Reason: readable bindings in one place; project.godot stores them as serialized objects.
- 2026-10-25: The hotbar holds every non-air block type. Reason: no inventory or resources until M3.
- 2026-10-25: A sand-coloured plane continues the seabed outside the map. Reason: otherwise the map's square edge shows through the water.
- 2026-10-25: Player movement moved into Sim (`PlayerMovement`): a box swept against the block grid one axis at a time. It replaces the `CharacterBody3D` player, godot_voxel's collision mesh and Godot physics interpolation from M1a (the camera now interpolates between ticks by hand). Reason: the server has to run every player from their inputs without a renderer, and client prediction only stays in step if both run the same code.
- 2026-10-25: Hand-written RPCs and snapshots (`Net/Replicator`, `Sim/Protocol/WireFormat`) instead of `MultiplayerSynchronizer`/`MultiplayerSpawner`. Reason: input-driven prediction and reconciliation don't fit property syncing, and the plan expected custom replication by M3 anyway.
- 2026-10-25: Server and client root nodes are both named `Game`, so the one `Replicator` node sits at `/root/Main/Game/Replicator` on both sides. Reason: Godot calls an RPC on the node at the same path.
- 2026-10-25: Channels: world, edits and hash replies on reliable channel 0 (so a hash reply follows every earlier edit); inputs on unreliable-ordered channel 1, repeating the last 4; snapshots on unreliable-ordered channel 2 at 20 Hz; other players drawn 100 ms in the past. Rates are in `data/net.json`. Reason: inputs and snapshots are replaced by the next one, so they needn't be reliable.
- 2026-10-25: The server runs at most one input per tick per player on average (a budget capped at `max_input_backlog`) and at most `max_edits_per_second` edits. Reason: a client sending inputs or edits faster than real time mustn't move or build faster.
- 2026-10-25: Clients apply their own edits at once (prediction). The server re-checks them with `BuildRules`; on rejection it sends that client the real block. Reason: building feels instant, and the server still decides.
- 2026-10-25: Flying (noclip) is allowed by the server in M1. Reason: a building aid while testing; it's a cheat in a real match, so decide before M2.
- 2026-10-25: On join, the server sends its `data/*.json` text, the seed, every edit and its world hash; the client rebuilds and checks the hash. Reason: identical terrain and movement tuning on both sides, and the hash catches drift. For M1 the edits go in one message; split them per chunk when craters make it big.
- 2026-10-25: Players spawn on a ring of 8 spots around the island centre. Reason: players joining together would otherwise stand inside each other.
- 2026-10-25: The automated sync test is two headless bot clients (`--bot=builder|breaker`) run by `build synctest`. Reason: the plan's bot sync test; the late-joining breaker also tests late join.
- 2026-10-25: The plane's arcade flight model is in Sim (`PlaneFlight`), run by the server and predicted by the pilot's client, like walking. Speed lives along the nose; below the stall speed the plane sinks; climbing costs speed and diving gives it back; a banked plane turns on its own. Reason: arcade, not simulation (game plan), and prediction needs the same code on both sides.
- 2026-10-25: Plane controls reuse the player input: W/S pitch (S pulls up), A/D roll in the air and steer on the ground, Shift/Ctrl throttle, Space brake, E to get in and out. No rudder key. Reason: one input packet for everything, and fewest keys to learn.
- 2026-10-25: Planes treat the sea surface as solid ground. Reason: gives an endless flat runway around a hilly island, and avoids planes sinking to the seabed. Revisit when ships and crashes arrive.
- 2026-10-25: The plane collides as an upright box (2 x 1.4 x 2) using the same block sweep as players (`VoxelBox`); wings can overlap blocks. Hitting a wall stops it dead, with no damage. Reason: simplest thing for M1; damage arrives with weapons.
- 2026-10-25: Getting in and out is decided by the server, on the input that pressed E, and not predicted. The client sees the change one round trip later. Reason: only the server knows if the seat is free; the delay is short enough for M1.
- 2026-10-25: The single-player sandbox has no plane. Reason: planes are server entities; play M1c with a local server.
- 2026-10-25: Planes are drawn from boxes (`PlaneModel`) and seen through a chase camera that follows heading and half the pitch, not roll. Reason: placeholder art; a rolling horizon is hard to fly by.
- 2026-10-25: Bombs fly in Sim (`BombFlight`): gravity and drag, the move checked block by block so nothing tunnels, and the sea surface stops them. Hitting a block blasts a crater of radius `crater_radius` around it; the sea makes a splash and no crater. Tunables in `data/weapons.json`. Reason: same code for the server's real bomb, the clients' drawing and the bombsight.
- 2026-10-25: Left click in the air drops a bomb, through a `Fire` input button handled on its tick like `Use`; 1-second reload per plane; no bombs while on the ground. Reason: one key, and the server decides.
- 2026-10-25: Bombs aren't in snapshots. The server sends a reliable drop event (id, tick, position, velocity) and clients simulate the fall themselves; the server's explosion event carries the impact point and the crater edits in one message. Other players' bombs are drawn at the same delay as their planes, your own at the present. Reason: no per-tick traffic for bombs, and the crater stays authoritative.
- 2026-10-25: Craters can't remove the bottom layer, the same rule as breaking by hand (`VoxelWorld.UnbreakableLayer`). Reason: consistency, and nobody bombs a hole out of the world.
- 2026-10-25: Blocks have no gravity: whatever a crater leaves standing stays, floating if need be. Reason: Minecraft-style and simplest; revisit if floating towers spoil raids.
- 2026-10-25: The pilot sees a bombsight ring at the predicted impact. Reason: arcade, not simulation; dropping blind with a 50-block throw would be frustrating.
- 2026-10-25: The bomb doesn't damage players or planes yet. Reason: there's no health system before M2/M3.

## M2

- 2026-10-25: Two islands side by side along X, the east one a mirror image of the west (`island_spacing` in `data/terrain.json`; 0 still means one island). The map is 320 x 64 x 160 blocks with 80 blocks of sea between the beaches. Reason: neither team gets better ground, and generation stays a pure function of the seed.
- 2026-10-25: Teams are Red (west island) and Blue (east island). A joining player may ask for a team; it's honoured unless that team would be more than `max_team_imbalance` players ahead, otherwise they join the smaller team. Reason: friends can play together, and teams still stay even.
- 2026-10-25: Match presets live in `data/presets.json` (`compressed` and `full`), chosen with the server's `--preset=NAME`; `compressed` is the default. Reason: the game plan's two presets; small matches are the common case while playtesting.
- 2026-10-25: Clients say hello (name, team wish) after connecting; the server answers with the world and a roster of everyone's name and team, sent again on every change. A client that doesn't say hello in 10 seconds is dropped; a full server says why before disconnecting. Reason: names and teams need to exist before a player spawns.
- 2026-10-25: Names are cleaned on the server: letters, digits, spaces and `-_.` only, at most 16 characters, made unique with a number. Reason: readable labels, and no impersonating someone already playing.
- 2026-10-25: Noclip flying is allowed only on a server started with `--dev` (developer mode), which also lets any player pick any team. The server strips the fly button otherwise. Decides the M1 open question. Reason: noclip is a cheat in a real match; the test bots still need it.
- 2026-10-25: One plane per team, parked off the far beach of its island, facing out to sea. Only that team can fly it. Reason: take-off away from the enemy, and a team's plane is its own.
- 2026-10-25: The client opens on a menu (name, server address, team) that remembers the last name and address in `user://settings.cfg`; `--connect` skips it. Losing the connection goes back to the menu with the reason. Reason: the plan's lobby and join-by-IP, kept to one screen.
- 2026-10-26: A match runs Warmup, Countdown, Playing (phases 1 to 3), Ended, then back to Warmup (`Sim/Match/MatchFlow`, stepped by the server each tick). The countdown starts when both teams have `min_players_per_team` and is cancelled if one drops below. Reason: the plan's match timer, as a plain state machine that's easy to test.
- 2026-10-26: The world resets at the start of each match: regenerated from the same seed, planes moored, bombs cleared, everyone respawned. Clients get it as a fresh world message, the same path as a late joiner. Warmup is a free-for-all practice. Reason: a fair start; the map stays the same match to match for now.
- 2026-10-26: Phase timings, the time limit and the bomb crater radius per phase (`crater_radius_by_phase`) are per preset. Phase 1 has no bombs; phases 2 and 3 have radius 3 and 5 in both real presets. Reason: design pillar 1 (the clock drives escalation) and the plan's "nothing crosses water but scouts" in phase 1.
- 2026-10-26: Compressed: phase 2 at 8 min, phase 3 at 25, limit 45. Full: 20, 120, 180 (phase 1 short, per review note 6). Starting guesses to tune in playtests.
- 2026-10-26: Presets `quick` (5-minute match), `practice` (endless warmup) and `test` (20-second match) join `compressed` and `full`. Reason: demos and short playtests, the block sync test, and the automated match test.
- 2026-10-26: The match status (stage, phase, clock, winner, reason) rides in every snapshot rather than in separate events; clients announce changes by comparing. Reason: always current, survives packet loss, and late joiners get it for free.
- 2026-10-26: Input sequence numbers carry on across a world reset (the client's new prediction starts from the last number sent). Reason: the server ignores numbers it has already seen, so restarting at 1 would freeze the player.
- 2026-10-26: Reaching the time limit is a draw until scoring arrives in piece 4.
- 2026-10-26: Each island has an industrial core: a 7 x 5 x 7 box of a new `Core` block at the centre, on a levelled stone foundation, generated with the terrain (`core_size`, `core_height` in `data/terrain.json`). Reason: part of the seed, so every client has it with no extra network traffic, and it mirrors for fairness.
- 2026-10-26: Core blocks can't be broken or placed by hand. Bombs only destroy them within `core_blast_factor` (0.5) of their crater radius; nukes ignore that. Reason: conventional raids chip the core (it counts for the score in piece 4) without making the nuke pointless; repairing it comes with M3.
- 2026-10-26: Core health is the share of core blocks still standing. Clients count it from their own world. Reason: the world is already in sync, so no extra messages.
- 2026-10-26: The nuke stub: from phase 3 each team has a nuke, then another `nuke_cooldown_minutes` after each drop (per preset). Right click in the air drops it; it flies like a bomb and blasts a radius-9 crater. Landing within `nuke_hit_margin` (3) blocks of the enemy core's footprint ends the match with that team winning (reason CoreDestroyed). Reason: the plan's "stub the nuke as a special bomb" until the M4 pipeline; the hit counts on the site, so a core already bombed flat can still be hit.
- 2026-10-26: Spawns are on a ring just outside the core. Reason: nobody spawns on top of it.
- 2026-10-26: Conventional bombs reducing a core to 0% don't end the match. Reason: only a nuke on the core wins outright (game plan); the score in piece 4 will reward core damage.
- 2026-10-26: Time-limit score: the team that kept more of its core standing wins; level cores are a draw. Decides the plan's open score question. Reason: simplest rule that makes conventional raids count without a nuke, and it's visible all match on the core line.
- 2026-10-26: Concede vote: F10 toggles your vote; a team concedes once `concede_fraction` (0.66, per preset) of its players, rounded up, have voted, so a one-player team concedes on its own vote. Only during play; votes reset at each match start. Reason: the plan's concede vote, with a threshold that one sulking player can't trigger in a full team.
- 2026-10-26: Rejoin by identity token: each client keeps a random token in `user://settings.cfg` and sends it with hello; the server remembers the name and team of anyone who leaves during a match (until warmup) and seats them back there, whatever they ask for. Reason: the plan's rejoin after disconnect without accounts; a token, unlike a name, can't be claimed by someone else typing it.
- 2026-10-26: The roster carries each player's concede vote and ping, and is re-sent every 2 seconds as well as on changes. Reason: the scoreboard needs live pings; one small message per 2 s is cheap.
- 2026-10-26: The scoreboard is shown while Tab is held. Reason: the usual convention.

## M3

- 2026-10-26: Team build protection by ownership (the plan's "simplest option before M3"): every placed block records the placer's lasting player id and team. By hand, a player can break natural blocks, their own, the enemy's, and those of teammates who aren't on the server; never an online teammate's. Reason: one griefer can't tear down the team's base, and an absent player's work can still be cleared.
- 2026-10-26: Lasting player ids are assigned per identity token for the server's lifetime, so ownership survives a reconnect. Reason: the token already identifies a returning player (M2 piece 4).
- 2026-10-26: No friendly fire: a team's bombs and nukes make no crater on its own half of the map (Red west, Blue east); the bombsight shows white there. Reason: stops a teammate bombing their own base, with a rule that's easy to see and explain. Enemy blocks built on your half can still be broken by hand.
- 2026-10-26: Block owners travel with every edit and with the late-join world, and the world hash covers them. Reason: clients predict breaks with the same rule, and the sync tests catch ownership drift.
- 2026-10-26: Placing is not restricted (anyone may build anywhere). Reason: simplest first; revisit if players wall in teammates or block planes.

- 2026-10-26: A joiner whose identity token is already in use by a connected player is treated as a new player (fresh player id, no claim on that seat or those blocks). Reason: two windows on one machine share a token, and protection must still tell them apart; it also stops one token being used by two people at once. Such a joiner can't reclaim a seat after a disconnect.
- 2026-10-26: **The industrial core is removed.** A nuke landing on solid ground anywhere on the enemy island (the enemy's half of the map) wins; a splash in the sea doesn't. Teams decide where to hide their equipment. Supersedes the core, core protection, core health and the core-based time-limit score from M2 piece 3 and 4. Reason: developer decision; hiding the pipeline makes the nuke and recon matter.
- 2026-10-26: Reaching the time limit is a draw until a score is designed. Reason: developer decision to decide scoring once the economy exists.
- 2026-10-26: The `Core` block id (6) is retired, not removed: never generated or placeable. Reason: block ids are never reused.
- 2026-10-26: Island direction set by the developer (`docs/island-sketch.png`): big islands (about two minutes to walk across), identical and mirrored for now, with mountains at the far end, forests, hills and grassland facing the strait. Built the same day (see below).
- 2026-10-26: Next order of work: the big sketch-based islands, then foundations (server split into systems, a generic replicated object and structure model, team state), then resources against the developer's tech tree.
- 2026-10-26: **Big islands built from the sketch.** Map 93 x 8 x 25 chunks (1488 x 128 x 400 blocks), sea level 32; each island fills a 600 x 300 box (two minutes' walk at 5 blocks/s), 160 blocks of strait. The coast is a piecewise outline traced from the sketch, roughened by domain-warped noise; a chamfer distance transform from the coast gives the underwater slope, a 12-block beach and the rise inland. Mountains (ridged noise, +60), hills (rounded, +12 to +24) and forests are elliptical regions in `data/terrain.json`. Reason: developer's sketch and size.
- 2026-10-26: New block ids Wood (7), Leaves (8) and Ore (9). Ore is one generic kind until resources are designed; it can't be placed. Ore comes in clumps: 12% of clumps hold ore at the heart of the mountains (about 7% of the stone), 1.2% elsewhere (about 0.8%). Reason: "densely packed in the mountains, but can be found everywhere with lower probability"; distribution to be revisited with the tech tree.
- 2026-10-26: Generation computes the west half and copies it mirrored, block for block (trees and ore included), so the islands are exactly equal. Reason: balance while the islands are identical.
- 2026-10-26: Chunks that are all one block store no array (sparse chunks), and the world hash is built from per-chunk hashes. The full map generates in about 0.25 s (release build) with about 70% of chunks uniform. Reason: a 76-million-block map must stay cheap for the server and every client.
- 2026-10-26: Clients draw only the terrain around the camera (godot_voxel viewer following the player; chunks handed over nearest first, up to 64 a frame, dropped when godot_voxel unloads them), with depth fog at the draw distance: 224 blocks on foot, 384 flying (`data/view.json`). The Sim world still holds the whole map for collision, prediction and hashing. Reason: drawing the whole big map at once is too slow.
- 2026-10-26: Planes moor off the south beach in line with the island centre, facing south. Reason: the far ends are mountains now, and the south shore is open water away from the strait.
- 2026-10-26: Bot clients run in a window draw what they see (`BotView`), for watching and recording bot runs; headless runs are unchanged. Reason: recordings of flights over the big map.
- 2026-10-26: **The server game lives in Sim (`Sim/Server`), not in the Godot node.** `GameServer` is split into systems sharing one `ServerState`: Sessions, MatchSystem, Movement, Vehicles, Weapons, Building, Structures, TeamStates and Replication. `ServerMain` is a thin engine host: it opens the port, forwards network events, ticks the game, and implements `IServerTransport` over the Replicator. Reason: the server was one 770-line node and about to grow a whole economy; in Sim it can be unit-tested end to end with a fake transport, with no engine. `GameData` and the network message records moved to Sim for the same reason.
- 2026-10-26: **Generic replicated objects.** A `GameObject` has an id (never reused), a kind (from `data/structures.json`), team, owner, origin, facing (quarter turns), health and a bag of named integer values for whatever its kind needs to remember (stock, progress, fuel), so new kinds need no new message types. The server sends an object whole, reliably, whenever it appears or changes, and its id when it goes; joiners get every object with the world. The sync hash covers objects too (`GameHash`). Fast movers (players, planes, bombs) stay on the unreliable snapshot path. Reason: the tech tree will bring many kinds of machine; one replicated shape for all of them.
- 2026-10-26: **Structures are block entities.** A structure fills its footprint with `Block.Structure` (id 10), so players collide with it and bombs land on it through the ordinary voxel code, and those blocks travel as ordinary edits (before the object, on the same reliable channel). They can't be placed or broken one by one; craters leave them standing, and a blast instead takes `structure_damage` (50; nuke 1000) off every structure it reaches, destroying it at 0. Taking a structure down by hand follows team build protection, like blocks. Reason: Minecraft tech mods work this way, and hiding machines in the terrain is the point of the no-core design.
- 2026-10-26: Three placeholder structures (crate, depot, workshop) until the tech tree: they show placement, sync, damage and destruction, not function. No cost yet, no placement preview on other clients, no prediction (a structure appears when the server confirms it, one round trip).
- 2026-10-26: **Team state:** one `TeamState` per team (for now a stock of named resources), sent only to that team's players, on join, on every change and at a match reset. Reason: shared team resources are the likely model (open question with the economy); secrecy keeps the enemy from reading your stockpile off the wire. Nothing fills the stock yet.
- 2026-10-26: Every client still receives every structure, the enemy's included, since it receives every block anyway. Hiding the enemy's equipment from the network (fog of war against cheats) is a later concern; noted here so it isn't forgotten.
- 2026-10-26: **Eras replace the plan's milestones for the economy,** from the developer's draft (kept outside the repo): T1 Stone Age (10 min) through T8 WWII and T9 Cold War, built era by era. Teams advance by their own research (developer decision); the average times are balancing targets, not clocks. Planes, bombs and the nuke will move to their eras (WWI onward) when research lands; until then they stay as they are.
- 2026-10-26: **Mining is hold to mine** (developer decision): each block has a hardness in seconds (`data/items.json`), tools will divide it. The server checks the time since the player's last mine against the block's hardness (with `mining_slack_seconds` for network timing), so a cheat can't mine faster than holding the button would.
- 2026-10-26: **Items go into a small personal backpack (40, any mix), then into team storage** (developer decision). Storage structures (crate 200, depot 1000) hold items in their object values; what they hold belongs to the team, only that team can use them, and it's lost if they're destroyed. A team's stock (TeamState) is the sum of its storage. A full backpack loses what's mined. Storage must be empty to take down. Backpacks are kept for a player who drops out mid-match and emptied at each match start.
- 2026-10-26: Placing a block uses one of its item; blocks with no item (grass, leaves) can't be placed outside creative. Structures are still free until crafting (Stone Age piece 2).
- 2026-10-26: Presets can be `creative` (practice, test, nuketest): no items needed or gathered, instant mining, as in Minecraft's creative mode, so the sandbox and the automated tests build freely. Real matches (quick, compressed, full) gather everything.
- 2026-10-26: Ore splits into kinds: copper (common), tin (scarce, mostly in the mountains), iron and coal, generated now so the map won't change when later eras arrive; clay comes in clumps in the beach sand. - 2026-10-26: **Crafting:** recipes in `data/items.json`, made by hand (C, anywhere) or at a station structure of your team within reach (E; the workbench for now). Instant, no craft time yet. Ingredients come from the backpack first, then the team's storage (any of its crates and depots, in id order: logistics are abstracted until a later era); the result goes into the backpack, and crafting is refused if it won't fit. In creative presets crafting is free.
- 2026-10-26: **Tools:** items with a kind (axe, pickaxe), a tier and a speed. Blocks name the tool kind that speeds them up and the tier they need (0: bare hands will do). The best matching tool carried in the backpack is used automatically; there's no held tool and no wear yet. Stone tools (tier 1) mine copper, tin and coal; iron needs tier 2 (the Bronze Age's pickaxe), so it can't be mined in the Stone Age.
- 2026-10-26: **Structures cost materials** (`cost` in `data/structures.json`), paid like recipes: backpack first, then team storage. Taking one down by hand refunds its cost into the backpack (what doesn't fit is lost); a destroyed one refunds nothing. The placeholder workshop is replaced by the workbench.
- 2026-10-26: **The furnace** (Stone Age piece 3): a structure (12 stone, 4 clay) with three item slots kept in its object values as `slot:item` (input, fuel, output; 32 items each). The server steps every furnace twice a second: with something that smelts in the input, room in the output and fuel burning (or in the fuel slot to light), progress builds up to the recipe's seconds and one item turns into its result. Fuel only burns while something is smelting. Smelting recipes and fuel seconds are in `data/items.json` (copper and tin ore to ingots in 5 s; logs to charcoal in 8 s; logs burn 15 s, planks 5, charcoal 30, coal 40). Changed furnaces go to every client as object updates, so everyone sees the same state.
- 2026-10-26: Moving items generalises to a structure's slot (storage's `item`, a furnace's three); a furnace takes only what smelts into its input and what burns into its fuel, and nothing into its output. What's in a furnace isn't team stock: ingots count once they're put in storage. Any structure holding items must be emptied before it's taken down. Basics only, to be refined: no multi-block furnaces (the Iron Age's), no heat, no automation.
- 2026-10-26: **Research and eras** (Stone Age piece 4), from the developer's tech tree: `data/techs.json` lists the eras (Stone Age to the Cold War, with the developer's average minutes as balancing targets) and the techs. Each team researches on its own. Each era has its own points pool, earned by what the team's players do once they've reached it (Stone Age: chopping logs and mining stone, a point a block; Bronze Age: smelting bronze, 2 an ingot, and placing stone, 1). A tech costs points from its era's pool, can cost items too (paid like crafting), and can require other techs. An era moves on when its advance techs are all researched (the Stone Age with Bronze working; the Bronze Age's way on, the blast furnace, comes with the Iron Age). The era, points and researched techs are part of the team state, so only the team sees them.

- 2026-10-26: **Health, death and archery** (Bronze Age piece 1): players have 100 health (`data/player.json`). At 0 they die: they can't move or act, they vanish for everyone else, and after 5 seconds they're back at their island with full health. What they carried is left in a dropped backpack where they fell, a 1-block loot structure anyone of either team can empty (nothing goes in; it's not stock; it goes once empty, and a blast can destroy it). Archery (Bronze Age, 15 points) unlocks a bow and arrows at the workbench. On foot the trigger shoots the bow, if the player carries a bow and an arrow (creative: free); the server flies the arrow (`arrow` in `data/weapons.json`: 40 blocks/s, gravity 15, 25 damage, 0.8 s between shots) and decides hits. Arrows hurt only the other team's players on foot, stop at blocks and the sea, and do no block damage. Clients fly the same arrow to draw it. The bow is the hotbar's last slot. Nothing else does damage yet (no falling or bomb damage to players).
